# Design

## Context

See proposal.md - Why. After the three earlier changes:

- `runtime`: `SceneLoading` loads a project's scenes into an Ashley `SceneEngine`; games register components with
  `@SceneComponent` / `@Field` and export `components.schema.json` with `SchemaExportMain`.
- `physics`: `PhysicsWorld` (fixed 1/120 s steps, forces, kinematic moves, ropes with measured tension, pose
  write-back), the physics components, `PlayModule` / `PlayHostMain`, and `PlayExportMain` for `play.json`.
- `core`: model, terrain and sky loading. `TerrainMesh.draw(program, blank)` takes the caller's shader (uniforms
  `u_terrainSize`, `u_hasSplat`, `u_splat`, `u_has_<layer>` / `u_<layer>`; attributes position, normal, texcoord0);
  `Sky.draw(camera, sun)` draws a sky. `core` also has a terrain generator (`terrain/generation`).
- The plugin's terrain shader (`sceneview/terrain/TerrainShader`) depends on the Scene view's lights, fog and shadows,
  so it is not reusable by a game.

## Goals / Non-Goals

**Goals:**

- Every rule in `control-line-flight` and `control-line-scoring` is checked by a JUnit test with no window and no GL
  (physics natives only).
- The game's behaviour comes from scene data: planes, their numbers and the field are edited in Abyssus.
- One flight implementation serves both the game and Play in Abyssus.

**Non-Goals:**

- Shadows, PBR or the Scene view's lighting in the game; a simple lit look is enough.
- Moving the plugin's terrain shader into `core`.

## Decisions

### 1. Module and packages

`games/control-line` (`:games:control-line`): Kotlin JVM 21, `application` plugin with `mainClass`
`net.nevinsky.abyssus.games.controlline.MainKt`, depending on `:physics` (so `runtime`, `core`, `gdx-model`), the
full `gdx-backend-lwjgl3` with `gdx-platform:natives-desktop`, and jolt-jni natives for the build machine at runtime.

| Package (`...games.controlline.`) | Holds | GL / Swing |
|---|---|---|
| `components` | `PilotComponent`, `PlaneComponent`, `ControlLineComponents` (registry incl. physics) | none |
| `flight` | `Aero` (forces from state, pure), `LineRig` (handle body and ropes), `FlightSystem`, `FlightOutcome` | none |
| `track` | `SphereTrack` (pose -> azimuth, elevation, climb angle, inverted), maneuver detectors | none |
| `score` | `ScoreKeeper` (laps, points, combo), `ScoreTable` (file) | none |
| `flow` | `GameFlow` (screen state machine), `HandleInput` (keys / mouse -> tilt) | none |
| `screens`, `render` | libGDX screens (Scene2D), `FieldRenderer`, terrain shader, HUD | GL |
| `play` | `ControlLinePlay : PlayModule` | none |

### 2. Bundled project and assets

`games/control-line/project/ControlLine/`: `ControlLine.abss`, `scenes/Field.scene`, and `assets/`. The field
scene holds: `Field` (terrain + `HEIGHT_FIELD` collider), `Pilot` (`PilotComponent`, a kinematic rigid body with a small sphere collider and a simple figure model, at the circle's centre), the sky,
a directional sun light, and three parked planes (`Racer` SPEED 21 m, `Stunter` STUNT 18 m, `Trainer` TRAINER 15 m),
each with `PlaneComponent`, a dynamic `RigidBodyComponent` and a `CONVEX_HULL` collider.

- **Plane models:** three small low-poly glTF planes and a pilot figure generated by a checked-in script
  (`games/control-line/tools/PlaneModels.kt`, run by a `generatePlaneModels` task); the generated files are
  committed, so no art licence question arises.
- **Terrain:** a gently rolling 200 m field with a flat 50 m circle, generated once with `core`'s terrain generator
  and committed as an ordinary native terrain asset (`format: "abyssus"`, `formatVersion: 1`).
- **Sky:** a copy of `Untitled`'s procedural `skybox_physical`.
- **`abyssus/components.schema.json`** is committed (stable output); **`abyssus/play.json`** holds absolute paths, so
  it is git-ignored and written by `./gradlew :games:control-line:exportAbyssus`.

### 3. Flight model

Air density 1.225 kg/m³. From the body state each step (in `Aero`, pure):

- Airspeed `V`, angle of attack `a` from the velocity in the plane's frame; `q = 0.5 rho V^2`.
- Lift `q S CL`, with `CL = liftSlope * a`, capped at stall (|a| > 15° keeps the stall value and doubles drag).
- Drag `q S (zeroLiftDrag + CL^2 / (pi * 6))` (aspect ratio 6, fixed).
- Elevator moment `q S c * elevatorEffect * delta`, `delta = tilt * 20°` (decision 4); pitch damping
  `-pitchDamping * q S c * (c * omega_pitch / 2V)`; fixed small yaw and roll damping and a fin side force for lateral
  stability.
- Thrust along the nose, rotated outward by `engineOffset`, while fuel lasts; `rudderOffset` adds an outward yaw
  moment, as real control-line planes use to keep the lines tight.
- Line drag: per line `rho * 1.0 * lineDiameter * L * V^2 / 8`, applied at the plane against its velocity (the
  classic equivalent for a line whose speed grows from 0 at the handle to `V` at the plane).

`FlightSystem` applies these through `PhysicsWorld`'s body facade before each step. The constants that are not fields
(aspect ratio, stall angle, damping of the lateral axes) are named in `Aero` and tuned in task 4.4.

### 4. Lines, handle and control

The scene's `Pilot` entity is the handle body: a kinematic `RigidBodyComponent` with a small sphere collider.
`PhysicsWorld` only builds bodies from components when it is created, so game code cannot add a separate handle body
later. `LineRig` puts the plane at takeoff with `PhysicsBody.setPose` (added to `physics` by this change) and adds two
ropes of the plane's line length, from points `handleSpacing / 2` above and below the pilot's position plus
`handleHeight` to the plane's up and down leadouts. Both points lie on the pilot's vertical axis, so turning does not
move them. Before each step it turns the pilot to face the plane's azimuth (`moveKinematic`). The ropes stay equal length;
handle tilt drives the elevator directly, gated by tension (`control-line-flight`, "Control only through taut lines"):
`delta = tension >= 1 N ? tilt * 20° : 0`. This keeps the rope geometry simple while giving the real failure mode:
no tension, no control.

**Alternative rejected:** making tilt change the two ropes' lengths and computing the bellcrank from their difference.
More faithful, but rope length changes of a few millimetres fight the solver's tolerance at 120 Hz.

### 5. Flight outcome

`FlightOutcome` watches each step: ground contact (a `PhysicsWorld` contact between the plane and the field) with
speed > 3 m/s or the plane's up vector below the horizon -> crash; tension < 1 N for 2 s while airborne -> crash
"lines went slack"; contact upright at <= 3 m/s after the engine stopped -> landing. "Airborne" means more than 0.5 m
above the terrain under the plane.

The speed of a touch is the plane's sink speed just before it (how fast it came down onto the ground), not the
contact's whole relative speed: the planes glide at about 8 m/s, so measuring the whole speed would make every landing
a crash. Ground contact counts only once the plane has been airborne, so the takeoff run never ends a flight (an
upside-down contact always does).

### 6. Track and maneuvers

`SphereTrack` converts each step's pose, relative to the handle, into azimuth, elevation, the climb angle (the
velocity's angle within the sphere's tangent plane, 0 = along the circle, 90° = straight up) and an inverted flag (the
plane's up vector pointing away from the sphere's local up). Detectors are small state machines over these samples
with the thresholds in `control-line-scoring`: loops track the unwrapped climb angle, the inverted lap tracks azimuth
while inverted, the wingover tracks elevation and the azimuth flip, and figure 8 pairs loops within 2 s and cancels
their individual scores. `ScoreKeeper` adds lap points, maneuver points times the multiplier, and the landing bonus.
Tests feed recorded or synthetic sample sequences, so they need no physics.

### 7. Score table file

`ScoreTable(file: Path, json)` reads and writes `~/.abyssus-control-line/scores.json` (`{version: 1, entries: [...]}`)
through a temp file and an atomic move. A read failure renames the file to `scores.json.bad` and starts empty, with a
flag the score screen shows. The path is a constructor argument, so tests use a temp folder.

### 8. Screens and flow

`GameFlow` is a pure state machine (`MainMenu`, `PlaneSelect(index)`, `Flying(plane)`, `Paused`, `GameOver(result)`,
`NameEntry`, `Scores(from)`) with the transitions of `control-line-game-flow`; libGDX screens only render a state and
send events to it. UI uses Scene2D with libGDX's sample `uiskin` (Apache-2.0) bundled in resources. `FieldRenderer`
loads the field scene's assets through `core`'s `AssetLoading` (models, terrain, sky), draws models with libGDX's
default shader and an `Environment` from the scene's sun light, terrain with the game's own small shader (base layer,
splat layers, one directional light, fog) against `TerrainMesh.draw`, the sky with `Sky.draw`, and the lines with a
`ShapeRenderer`. The flight camera sits at the handle at eye height and looks at the plane.

### 9. Input

`HandleInput` is pure: it holds key state (W / Up, S / Down) and the last mouse Y, and produces a tilt in [-1, 1]
ramping at 1 / 0.15 s for keys, with the last-used device winning. The game feeds it from an `InputProcessor`; the
play module feeds it from the play protocol's `input` events, so both behave alike.

### 10. Play in Abyssus

`ControlLinePlay` registers `ControlLineComponents`, finds the plane (the selected entity if it has a
`PlaneComponent`, else the first plane by name), and adds `LineRig`, `FlightSystem` and `FlightOutcome` as systems. On
a crash or landing it restarts the flight from takeoff after 1 s and reports score, laps and tension as telemetry. The
module's `exportAbyssus` task runs `SchemaExportMain` and `PlayExportMain`.

### 11. Threads

| Piece | Thread | GL / native |
|---|---|---|
| Everything in the game (flow, physics step, flight, scoring, rendering, score file at GAME OVER) | the LWJGL3 main thread | GL and Jolt |
| `ControlLinePlay` systems | the play host's loop thread | Jolt |
| Tests | JUnit thread | Jolt only |

`Gdx.*` here belongs to the game's own process, so `GdxRuntime` is not involved.

## Risks / Trade-offs

- **Tuning a 6-DOF model takes time.** → Task 4.4 is a dedicated tuning task with the flight tests as its exit
  criterion; the field values are scene data, so tuning needs no rebuild once the code is right.
- **Lateral instability (planes rolling into the circle).** → Outward rudder and engine offset, fin side force and
  roll damping; the "Half a lap" and level-flight tests catch it.
- **Maneuver thresholds feel unfair.** → Thresholds live in one place, and the detectors are tested on recorded paths
  from real test flights (saved as fixtures by a test helper).
- **`play.json` with absolute paths.** → Git-ignored and regenerated by `exportAbyssus`; the README says so.
- **Plane models from a script look basic.** → Accepted for a test game; a designer can replace them in Abyssus.
- **Native and GL dependencies in `check`.** → Flight tests need the build machine's Jolt natives (as `physics`
  does); no test opens a window.

## Migration Plan

New module only; nothing existing changes. Rollback is removing the module from `settings.gradle.kts`.
